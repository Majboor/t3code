# Multi-Tenant Foundations

This document records the first implementation boundary for the public multi-user roadmap:

- #15 multi-tenant product foundations

- #30 roles and permissions

## Boundary Model

T3 Code must not host multiple tenants' code, credentials, sessions, or provider homes inside one shared runtime protected only by `tenant_id` checks. A tenant runtime is the filesystem and process boundary for hosted use.

The contract module `packages/contracts/src/tenancy.ts` defines the shared shape for:

- users, organizations, tenants, memberships, workspaces, and invites
- tenant runtime isolation paths and internal-only bind address
- provider-account ownership and per-user provider homes
- auth session to tenant session mapping
- public access limits and usage counters
- collaboration presence and authorship activity events
- product analytics events for prompts, token usage, credits, collaboration,
  workflow deliveries, and message metadata

## Runtime Isolation

A hosted tenant runtime has its own:

- Linux user or container identity
- base directory
- userdata/database directory
- secrets directory
- attachments directory
- worktrees directory
- run/session directory
- provider homes directory
- internal-only host and port

The control plane routes authenticated traffic to the runtime. Tenant runtimes must not be public internet endpoints.

The v1 runtime layout is generated by `deriveTenantRuntimeDirectoryLayout` from
`@t3tools/shared/tenancy` and follows this shape:

```txt
/opt/t3-tenants/{tenantId}/
  data/
    userdata/
      secrets/
      attachments/
  runs/default/
  worktrees/
  provider-homes/
  logs/
```

Runtime directories should be created with `0700` permissions and owned by the
tenant runtime Linux user. `validateTenantRuntimeIsolation` rejects runtime
descriptors that run as `root`, expose a public bind host, or place data,
secrets, attachments, worktrees, runs, or provider homes outside the tenant
base directory.

Server-side runtime provisioning starts in
`apps/server/src/tenancy/runtimeProvisioning.ts`: it derives the shared layout,
creates every runtime directory recursively, applies `0700`, and validates a
runtime isolation descriptor before any start path should launch a process.

The v1 systemd service template is generated by
`deriveTenantRuntimeSystemdUnit` from `@t3tools/shared/tenancy`. The generated
unit is named `t3-tenant-runtime@{tenantId}.service`, runs as the tenant Linux
user and group, uses the tenant base directory as `WorkingDirectory`, exports
tenant/runtime/path metadata through environment variables, and starts
`/usr/local/bin/t3-runtime serve` by default.

The initial runtime implementation target is `systemd-per-tenant` with:

- a distinct non-root Linux user such as `t3-{tenantId}`
- bind address `127.0.0.1`, `::1`, or a private network address only
- authenticated control-plane routing as the only public entrypoint
- memory, CPU, process/task, file-descriptor, temporary-directory, and writable
  path limits applied by the service manager
- protected host paths for system directories, other tenants, provider homes,
  secrets, logs, and runtime state outside the tenant base directory

The default generated service policy includes:

| Control           | Default                                                                     |
| ----------------- | --------------------------------------------------------------------------- |
| Restart policy    | `Restart=on-failure`                                                        |
| Stop behavior     | `TimeoutStopSec=30s`                                                        |
| Privilege guard   | `NoNewPrivileges=true`                                                      |
| Temporary files   | `PrivateTmp=true`                                                           |
| Host filesystem   | `ProtectSystem=strict`                                                      |
| Home directories  | `ProtectHome=true`                                                          |
| Memory ceiling    | `MemoryMax=2G`                                                              |
| CPU ceiling       | `CPUQuota=200%`                                                             |
| Process ceiling   | `TasksMax=512`                                                              |
| File descriptors  | `LimitNOFILE=8192`                                                          |
| Egress policy     | `IPAddressDeny=any` plus scoped `IPAddressAllow` for loopback/private binds |
| Writable paths    | `ReadWritePaths={tenantBaseDir}`                                            |
| Hidden host paths | `InaccessiblePaths=/root /home /var/lib/t3/secrets`                         |

Runtime lifecycle decisions are modeled by `evaluateTenantRuntimeLifecycle`
from `@t3tools/shared/tenancy` so the future supervisor can use one policy for:

- on-demand start from `stopped` only when the isolation descriptor validates
- denying start for unsafe runtime descriptors before provisioning or launching
- marking `starting` runtimes as `running` after a passing health check
- stopping `running` runtimes after their tenant idle shutdown window elapses
- stopping `running` runtimes after the public wall-clock ceiling elapses
- restarting unhealthy runtimes after 3 consecutive failed health checks
- quarantining unhealthy runtimes after 5 consecutive failed health checks
- cleaning up `stopping` runtimes once the stop has completed

Server-side supervisor integration starts in
`apps/server/src/tenancy/runtimeLifecyclePlanner.ts`: it evaluates known runtime
descriptors with the shared policy, current demand, last-activity timestamps,
and health snapshots, then returns both full and actionable lifecycle plans.
It also derives deterministic execution steps that map lifecycle actions to
idempotent process or state operations such as provision-and-start, stop,
restart, quarantine, mark-running, and mark-stopped. The eventual runtime owner
starts in `apps/server/src/tenancy/runtimeLifecycleSupervisor.ts`: it executes
those steps sequentially through an injected process adapter, skips previously
completed idempotency keys, fails with the offending step when execution fails,
and records lifecycle outcome metrics for executed, skipped, and failed steps.
The first concrete adapter is
`apps/server/src/tenancy/runtimeSystemdExecutor.ts`, which maps process lifecycle
steps to `systemctl` command sequences for systemd-per-tenant runtimes while
leaving state-only steps local to the control plane.

Tenant storage operations are planned by `deriveTenantRuntimeStorageOperationPlan`
from `@t3tools/shared/tenancy` before any filesystem mutation runs. The v1
control plane should require the tenant runtime to be stopped or quiesced for
backup, restore, export, delete, and default-tenant migration operations.

| Operation         | Runtime state       | Destructive | Scope                                                                                                      |
| ----------------- | ------------------- | ----------- | ---------------------------------------------------------------------------------------------------------- |
| Backup            | stopped or quiesced | no          | data, worktrees, provider homes, logs                                                                      |
| Export            | stopped or quiesced | no          | data, worktrees, provider homes, logs; secrets only with provider management permission                    |
| Restore           | stopped             | yes         | verified archive into tenant base directory                                                                |
| Delete            | stopped             | yes         | tenant base directory only, after retention and final-backup policy                                        |
| Default migration | stopped             | no          | legacy userdata, worktrees, provider homes, attachments, and logs into the generated default tenant layout |

Current single-tenant installs should migrate into a first/default tenant by
moving the existing userdata, worktrees, provider homes, attachments, and logs
under the generated default tenant layout, then running the runtime as that
tenant user before enabling public signup.

## Auth And Tenant Mapping

Public auth is separate from current local Basic Auth and pairing-token flows. A hosted auth session maps to a user plus one active tenant context through `AuthTenantSessionMapping` and `TenantSessionContext`.

Supabase, or any other hosted auth provider, should terminate into this mapping instead of becoming the app's authorization model. Server code should authorize actions from the tenant session context and named permissions.

The auth session descriptor may advertise public Supabase browser configuration (`projectUrl`, `anonKey`, and optional `audience`) so the web app can initialize login/session-restore flows. Server-only Supabase credentials such as the service-role secret are never included in the descriptor and remain behind server secret storage.

## Roles And Permissions

The shared helper `@t3tools/shared/tenancy` owns role-to-permission mapping. Route handlers should ask for a named permission such as `session.prompt`, `file.write`, or `provider.manage` and fail closed when a session has no role.

The initial roles are:

- `owner`
- `admin`
- `developer`
- `pm`
- `support`
- `viewer`
- `platform-operator`

Platform operators can manage runtime availability and quarantine, but they are not automatically granted file or prompt access.

Tenant permissions are additive across a user's active tenant membership roles.
There are no deny overrides in v1. If a future workflow needs emergency access
revocation, the membership should be disabled or have the role removed rather
than depending on an allow/deny merge order.

| Role                | Primary capability boundary                                                                                                     |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `viewer`            | Read tenant, workspace, project, session, and files. Cannot prompt agents, write files, invite users, or use provider accounts. |
| `pm`                | Viewer plus workspace invites, project creation/editing, session creation, and agent prompting. No file write/upload access.    |
| `developer`         | PM plus file write/upload and provider-account use/connect for hands-on implementation work.                                    |
| `support`           | Tenant/workspace/session/file read plus audit and support-assist permissions. No prompt, write, provider, or runtime powers.    |
| `admin`             | Full tenant administration, membership, provider, runtime, audit, prompt, and file capabilities.                                |
| `owner`             | Same tenant capabilities as admin for v1; retained as the accountable ownership role for future billing/export/delete policy.   |
| `platform-operator` | Runtime quarantine/management and platform operation only; intentionally excludes file read/write, prompting, and providers.    |

Organization roles are evaluated separately from tenant roles. They authorize
employee, team, department, access-review, access-grant, and audit-management
surfaces for organization-backed tenants, but they do not implicitly grant
workspace/file/provider/session permissions inside a tenant runtime.

| Organization role | Primary capability boundary                                                                            |
| ----------------- | ------------------------------------------------------------------------------------------------------ |
| `viewer`          | Read organization metadata.                                                                            |
| `developer`       | Read organization metadata. Tenant development access must come from tenant membership.                |
| `pm`              | Read organization metadata, invite employees, and participate in access reviews.                       |
| `support`         | Read organization metadata and audit events. Tenant support access must come from tenant membership.   |
| `auditor`         | Read organization metadata, access reviews, and audit events.                                          |
| `manager`         | Manage employees, teams, departments, reviews, and audit visibility, but cannot grant elevated access. |
| `admin`           | Manager plus organization updates, employee disablement, and access grants.                            |
| `owner`           | Same organization capabilities as admin for v1; retained as the accountable corporate ownership role.  |

Core RPC authorization rules:

- WebSocket upgrade requires a valid local session or hosted auth session.
- Hosted tenant WebSocket admission also applies IP, user, and tenant
  connection ceilings before RPC dispatch.
- Workspace, project, session, thread, file, diff, collaboration, provider, and
  organization RPCs must check named permissions from the authenticated
  tenant/organization context.
- Workspace/file operations are authorized twice: first by named permission
  such as `file.read`, `file.write`, or `file.upload`, then by path/root
  checks that prevent escaping the workspace and tenant runtime boundaries.
- Agent prompt/turn start requires `session.prompt`; hosted provider session
  startup additionally requires `provider.use` for the selected provider
  account and must satisfy runtime/provider concurrency limits.
- Provider-account connect/status/confirm flows require `provider.connect` for
  private user-owned accounts. Tenant or organization shared account management
  requires `provider.manage`.
- Tenant runtime start, stop, restart, quota, and quarantine controls require
  `runtime.manage` or `platform.operate` depending on whether the action is a
  tenant-admin action or platform operations action.
- Support and platform-operator roles are audit-oriented and constrained:
  support can observe and assist only where explicitly granted, and platform
  operators can operate runtimes without receiving tenant files, prompts, or
  provider credentials by default.

## Workspace, Project, Category, And Session Hierarchy

The workspace hub should present one tenant-scoped working surface without
making a project, category, or session the security boundary. The tenant
runtime and membership context remain the isolation boundary; workspace
entities organize how a user finds and resumes work inside that boundary.

The v1 hierarchy is:

```txt
tenant
  workspace
    category or saved view
      project
        session/thread
          messages, activities, turns, checkpoints, terminals
```

Important ownership rules:

- A workspace belongs to one tenant and is the collaboration scope for shared
  presence, invites, workspace hub filtering, and future saved views.
- A project belongs to one workspace/tenant and represents a filesystem root or
  repository working area. The current orchestration projection stores
  `projectId`, `title`, `workspaceRoot`, repository identity, default model
  selection, scripts, timestamps, and `deletedAt`.
- A session is represented by an orchestration thread. A thread belongs to one
  project through `projectId`, carries runtime/model/branch/worktree metadata,
  and owns messages, activities, turns, checkpoints, proposed plans, terminals,
  and the current provider session projection.
- Categories are workspace-level presentation objects in v1. They group
  projects and threads for navigation, search, saved filters, and analytics
  rollups, but they do not own the project filesystem root and they do not move
  a thread between tenants or projects. The existing logical project grouping
  by repository/repository path is a derived category-like view, not a
  persisted ownership boundary.
- Task assignment is session-adjacent: tasks may point at a workspace, project,
  thread, message, proposed plan, or checkpoint, but task ownership should not
  replace the thread's canonical `projectId` or tenant authorization context.

Lifecycle and archive rules:

| Level            | Archive/delete behavior                                                                                                                                       |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Workspace        | Archive hides the workspace and its categories/projects from default hub views; destructive delete requires tenant export/backup policy.                      |
| Category/view    | Archive or delete only changes hub presentation. Projects and sessions stay in place.                                                                         |
| Project          | Soft delete hides the project and prevents new sessions by default; existing threads remain addressable for audit/export until retention policy removes them. |
| Session/thread   | Archive sets `archivedAt`, removes the active terminal/session surface, and should stop the provider session when present. Unarchive clears `archivedAt`.     |
| Messages/turns   | Append-only for audit. Redaction/delete should be modeled as explicit moderation or retention events rather than rewriting history.                           |
| Provider session | Ends when the thread is archived, deleted, interrupted, or when runtime lifecycle policy stops the owning tenant runtime.                                     |

Hub and analytics rules:

- Default hub views should exclude soft-deleted projects and archived threads,
  but archived threads must remain available through archive/search surfaces.
- Project ordering should use the freshest thread activity in that project,
  preferring `latestUserMessageAt`, then thread `updatedAt`, then project
  `updatedAt`.
- Thread ordering inside a project should use latest user activity first, then
  update time, while keeping archived threads out of the default list.
- Analytics events should carry tenant id, workspace id when available, project
  id, thread id, actor id, and category/saved-view id when the event is
  initiated from a categorized hub surface. Category ids are analytics
  dimensions, not authorization scopes.
- Collaboration presence may be workspace-wide or thread-specific. Presence
  records already include tenant, workspace, optional thread, and user
  identity; project/category-specific presence should be derived from the active
  thread or hub filter instead of introducing a second presence model.

## Provider Account Isolation

BYO Codex and Claude credentials belong to a provider account. Provider accounts are tenant-scoped and can be owned by a user, tenant, or organization. The default sharing mode is private per user.

Provider sessions carry the tenant id, user id, provider account id, provider home directory, and cwd used to start the provider. That context is the minimum audit and isolation envelope for hosted provider processes.

`deriveProviderAccountHomeLayout` from `@t3tools/shared/tenancy` derives the
provider account storage root under the tenant runtime's `provider-homes`
directory:

```txt
/opt/t3-tenants/{tenantId}/provider-homes/{userId}/{provider}/
  config/
/opt/t3-tenants/{tenantId}/data/userdata/secrets/provider-accounts/{userId}/{provider}/
```

`validateProviderAccountIsolation` rejects provider account auth/config
directories outside tenant provider homes and rejects provider secrets outside
tenant secrets. Provider homes must never live inside worktrees or project roots.

`evaluateProviderAccountAccess` is the shared authorization policy for selected
provider accounts:

- disabled provider accounts are denied
- account, session, and tenant session tenant ids must match
- provider session provider must match the account provider
- private user-owned accounts can only be used by the owning user
- tenant-owned accounts require `tenant-shared`
- organization-owned accounts require `tenant-shared` and the active
  organization id
- provider session homes must stay inside the selected account home
- provider session homes must not be inside tenant worktrees

`deriveProviderLaunchEnvironment` is the shared launch-time policy for hosted
Codex and Claude sessions. It calls `evaluateProviderAccountAccess` first and
returns an empty environment when account access is denied.

`deriveProviderAccountConnectionPlan` is the shared persistence planner that
connect/start flows should call after provider authentication succeeds. It
creates or reuses the user's private provider account, creates or reuses an
active provider session for the requested cwd, derives the isolated launch
environment, and returns the next provider-isolation snapshot for persistence.
The planner is idempotent for repeated starts and refuses to mint a launchable
session for disabled accounts.

Hosted WebSocket `thread.turn.start` authorization now persists this connection
plan for the authenticated tenant user before workspace/provider-session access
checks run. Public concurrency limits are checked before persistence, so
rejected over-limit turns do not create provider session records.

Hosted WebSocket also exposes redacted provider-account status APIs:

- `providerAccounts.list` returns provider, owner, sharing, connection status,
  creation/disabled timestamps, and active session counts for accounts visible
  to the authenticated tenant user. It intentionally omits auth, config,
  provider home, and secrets paths.
- `providerAccounts.connect` prepares the manual hosted connect bootstrap for
  Codex or Claude and returns redacted CLI setup/status instructions. It
  requires `provider.connect` and does not return provider home, config, or
  secrets paths.
- `providerAccounts.openAuthTerminal` opens a hosted provider auth terminal in
  the user's isolated provider home, creates the provider home/config/secrets
  directories with `0700`, launches the terminal with the account-scoped
  provider environment, and writes the redacted auth command for the user. It
  requires `provider.connect`.
- `providerAccounts.confirm` accepts the redacted provider status command
  output after the external login flow completes, rejects unauthenticated
  output without persisting anything, and calls
  `deriveProviderAccountConnectionPlan` to create or reuse the user's private
  provider account and active session only after confirmation succeeds. It
  requires `provider.connect` and `session.create`.
- `providerAccounts.disconnect` disables a visible account and marks any active
  persisted provider sessions for that account ended. Private user-owned
  accounts require `provider.connect`; tenant/organization-shared accounts
  require `provider.manage`.

For organization-backed hosted sessions, provider-account operations append
organization audit events for account creation, status checks, disconnects, and
launch use. Personal tenants skip organization audit writes because they do not
have an organization audit stream.

Provider session startup accepts this plan through `providerLaunchEnvironment`.
The provider command reactor attaches the plan when the thread workspace cwd is
covered by an active persisted provider session for the requested provider.
The Codex adapter forwards the isolated environment to the app-server manager
for both the version probe and `codex app-server` process. The Claude adapter
passes the isolated environment directly to the Claude SDK query options.

Allowed launches keep only explicitly safe inherited environment variables and
replace provider auth/config locations with tenant-scoped paths:

| Provider | Required launch environment                                                                                         |
| -------- | ------------------------------------------------------------------------------------------------------------------- |
| Codex    | `HOME={account.authHomeDir}`, `CODEX_HOME={providerSession.providerHomeDir}`, `XDG_CONFIG_HOME={account.configDir}` |
| Claude   | `HOME={account.authHomeDir}`, `CLAUDE_CONFIG_DIR={account.configDir}`, `XDG_CONFIG_HOME={account.configDir}`        |

All hosted provider launches also include `T3_TENANT_ID`, `T3_USER_ID`,
`T3_PROVIDER_ACCOUNT_ID`, `T3_PROVIDER_HOME`, and
`T3_PROVIDER_SECRETS_DIR` for audit correlation. Inherited global auth and home
variables are scrubbed before the provider starts, including `CODEX_HOME`,
`CLAUDE_CONFIG_DIR`, `HOME`, `XDG_CONFIG_HOME`, `OPENAI_API_KEY`,
`ANTHROPIC_API_KEY`, and `ANTHROPIC_AUTH_TOKEN`.

Claude Code supports `CLAUDE_CONFIG_DIR` as the replacement for `~/.claude`;
hosted launches still isolate `HOME` as defense in depth for any home-relative
fallbacks or adjacent provider state.

## Public Abuse Limits

`PublicAccessLimits` and `TenantUsageCounters` define the shared contract for:

- WebSocket connection ceilings
- RPC request ceilings
- RPC request payload ceilings
- file upload/read size ceilings
- directory listing and diff response size ceilings
- active turn ceilings
- active provider session ceilings
- provider-connect failure throttling and lockout
- active tenant runtime ceilings per machine
- idle and wall-clock runtime ceilings

The shared helper evaluates counters against limits so WebSocket, RPC, runtime, and file-operation paths can use the same semantics.

The initial public-hosting defaults live in `DEFAULT_PUBLIC_ACCESS_LIMITS` from `@t3tools/shared/tenancy`:

| Control                                        |      Limit |
| ---------------------------------------------- | ---------: |
| WebSocket connections per direct remote IP     |         60 |
| WebSocket connections per authenticated user   |          4 |
| WebSocket connections per tenant               |         40 |
| RPC requests per minute per authenticated user |        120 |
| RPC requests per minute per tenant             |      2,000 |
| RPC request payload bytes                      |     12 MiB |
| File upload bytes per operation                |     10 MiB |
| File read bytes per operation                  |      2 MiB |
| Directory entries per listing                  |      1,000 |
| Diff response bytes per request                |      2 MiB |
| Active agent turns per user                    |          2 |
| Active agent turns per tenant                  |         20 |
| Active provider sessions per user              |          3 |
| Active provider sessions per tenant            |         30 |
| Failed provider-connect confirmations per user |          5 |
| Provider-connect failure window                | 15 minutes |
| Provider-connect lockout                       | 15 minutes |
| Active tenant runtimes per machine             |        100 |
| Tenant runtime idle timeout                    | 15 minutes |
| Tenant runtime wall-clock ceiling              |   24 hours |

### WebSocket frame-size guardrail

The v1 hosted transport does not add a separate raw WebSocket frame cap below
Effect RPC dispatch. The installed `effect@4.0.0-beta.45`
`RpcServer.toHttpEffectWebsocket` and `layerProtocolWebsocket` options expose
tracing and fatal-defect controls, but no stable frame-size or message-size
limit. The current protocol helper upgrades the HTTP request and hands the
resulting socket directly to Effect RPC.

The platform server layers do not expose a portable hook either. The Node
platform creates its internal `ws` server with `noServer: true`, and the public
`NodeHttpServer.layer`/`make` options only accept HTTP listen and shutdown
settings. The Bun platform owns its `websocket.message` handler inside
`BunHttpServer.make`; passing a Bun websocket option through T3's server config
would be overwritten by the platform layer's own websocket handler and would
not apply consistently to Node test/runtime paths.

For now, decoded request-size enforcement remains the v1 public-hosting
control. Hosted sessions reject oversized decoded RPC inputs with typed RPC
errors, metrics, tenant/user attribution, and operation labels before invoking
the target handler. A lower-level frame cap should only be revisited when Effect
or the selected platform server exposes a stable per-route/server frame-size
option that can be configured without forking the upgrade pipeline.

Hosted provider authentication confirmation tracks failed status-output checks
per user, tenant, and provider. After 5 failed confirmations inside the
15-minute window, the confirmation endpoint returns a typed rate-limit error
for 15 minutes, records a public access limit rejection, and does not persist a
provider account even if a later status payload claims success during lockout.
Successful confirmation clears the failure bucket for that user/provider.

`planTenantRuntimeLifecycle` is the server-side handoff between persisted
tenant runtime descriptors and the shared lifecycle policy. Runtime owners can
pass known runtime records plus demand, last-activity, and health snapshots to
receive both a complete lifecycle plan and an actionable subset for starts,
idle shutdowns, wall-clock shutdowns, unhealthy restarts, and quarantines.
`deriveTenantRuntimeLifecycleExecutionSteps` turns that actionable subset into
stable, idempotent runtime-owner work items. `superviseTenantRuntimeLifecycle`
then dispatches those work items through the runtime owner's process adapter
and records `t3_tenant_runtime_lifecycle_actions_total` outcomes. The systemd
adapter provides the initial process implementation seam by translating runtime
owner operations into `systemctl daemon-reload`, `enable --now`, `stop`,
`restart`, and quarantine `stop`/`disable` command sequences.
Generated tenant runtime systemd unit files and completed lifecycle step
idempotency keys are persisted in the tenancy store so a runtime owner can
reload unit content and skip already-completed lifecycle work after a server
restart.
`superviseTenantRuntimeLifecycleWithRepository` is the durable runtime-owner
entrypoint: it loads completed step keys, materializes systemd unit files before
start operations, delegates to the existing process adapter, and only appends
completion records for successfully executed lifecycle steps.
Successful lifecycle actions also update the persisted runtime descriptor to
the shared policy target status, recording `lastStartedAt` for starts and
`lastStoppedAt` for stop-like actions so the next supervisor pass can continue
from the correct intermediate state.
`runTenantRuntimeLifecycleSchedulerOnce` is the current scheduler seam: a
single deterministic tick loads persisted runtime descriptors, applies
machine-level start admission against the public runtime cap, and invokes the
repository-backed supervisor with admitted demand plus health and activity
snapshots. Runtime maintenance such as idle or wall-clock shutdown still runs
even when new runtime starts are denied by machine admission.
`TenantRuntimeLifecycleOwnerLive` starts this scheduler as a scoped background
runtime during server startup. The owner now derives scheduler demand and
last-activity snapshots from active persisted provider sessions whose cwd or
provider home belongs to a known tenant runtime, then runs the systemd lifecycle
adapter on the resulting persisted runtime state. Provider-session `createdAt`
is retained as the conservative activity floor, and fresher
`provider_session_runtime.last_seen_at` records from active provider runtimes
replace that floor when the persisted runtime payload cwd belongs to the tenant
runtime. Active `starting` and `running` runtimes are probed with
`systemctl is-active <unit>` on each sweep. Passing probes let the shared policy
promote `starting` runtimes to `running`; failed probes are counted
consecutively in the runtime owner process so the existing restart and
quarantine thresholds can act on real systemd health instead of placeholder
state.

Limit decisions should return a typed error to the caller and emit an audit/metrics event with:

- the rejected limit key
- current counter value and configured maximum
- tenant id and user id when available
- operation family, such as `websocket.connect`, `rpc.dispatch`, `file.read`, `file.upload`, `provider.session.start`, or `runtime.start`
- request correlation id when available

Rejected hosted WebSocket/RPC decisions increment `t3_public_access_limit_rejections_total` with these attributes and also emit a structured warning log for trace/audit review.

## Local Multi-Tenant Seed

`apps/server/src/tenancy/localTestingSeed.ts` provides the reusable local
testing seed for this foundation layer. It creates:

- one personal tenant, one organization-backed corporate tenant, and one
  support tenant
- owner, developer, PM, and support memberships across those tenants
- personal, corporate, and support workspaces
- isolated tenant runtime descriptors under a configurable tenant root
- private user-owned Codex provider accounts under tenant provider homes
- collaboration presence and organization audit activity for smoke testing

The seed is intentionally small and deterministic. It is meant for local
testing and integration harnesses, not production bootstrapping. The companion
test verifies that seeded runtime descriptors pass isolation validation,
provider-account homes stay inside tenant runtime paths, public runtime limits
admit the seeded runtimes, and the full snapshot round-trips through the
tenancy persistence layer.
